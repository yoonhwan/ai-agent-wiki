1. 스택 개요 및 아키텍처

1.1 핵심 철학

본 스택은 "워크트리로 시작해 멀티 코딩툴을 멀티 에이전트로 역할에 맞게 돌리고, 모니터링하고, 결과를 받아내는 풀스택 바이브코딩" 을 실현한다. 개발 목표를 조사하고 세분화하여 스몰 태스크로 분해한 뒤, 멀티 에이전트로 병렬 진행시키고, 완료되면 PR 확인 후 머지하여 태스크를 마무리하는 일련의 작업 루프를 통해 최종 결과를 구현하는 구조이다.

1.4 통신 프로토콜 — JSONL 기반 상태 머신

모든 에이전트 간 통신은 JSON Lines (JSONL) 파일 기반 상태 머신 방식을 따른다. 각 에이전트 세션은 3개의 JSONL 파일을 보유하며, 팀 리더(Mayor)가 response.jsonl의 status + next_actor 필드를 읽어 다음 행동할 에이전트를 결정하는 상태 기계(State Machine)로 동작한다.

1.4.1 3파일 구조

| 파일 | 형식 | 역할 | 작성자 | 읽는 자 |

| --- | --- | --- | --- | --- |

| query.jsonl | JSONL | 작업 요청 (상위 → 하위) | Mayor / 팀 리더 | 실행 에이전트 |

| response.jsonl | JSONL | 작업 결과 + 상태 (하위 → 상위) | 실행 에이전트 | Mayor / 팀 리더 |

| history.jsonl | JSONL | 통신 이력 로그 (전체 추적) | 양쪽 모두 | 양쪽 모두 |

1.4.2 query.jsonl 레코드 스키마

{"id":"q-001","timestamp":"2026-02-17T10:00:00Z","from":"mayor","to":"agent-implement-1","bead_id":"gt-001","status":"QUEUED","task":{"title":"Prisma Comment 모델 스키마 정의","description":"Comment 모델 추가, User/Post 관계 설정, 마이그레이션","engine":"claude","model":"sonnet","effort":"high","branch":"feat/comment-model","worktree":"/tmp/wt/agent-1"},"context":{"prd_path":"PRD-comments.yaml","dependencies":[],"rules":["use TypeScript strict mode"]},"constraints":{"max_rounds":3,"timeout_minutes":30}}

Peer Review 요청."}

1.4.4 상태 코드 (11개 ) — 상태 머신 전이 규칙

| 상태 | 방향 | 설명 | 다음 가능 상태 |

| --- | --- | --- | --- |

| QUEUED | 상위 → 하위 | 작업 대기열 추가 | IN_PROGRESS |

| IN_PROGRESS | 하위 → 상위 | 작업 수행 중 | PENDING_REVIEW, ESCALATED |

| PENDING_REVIEW | 개발자 → 리뷰어 | 코드 리뷰 요청 | APPROVED, REVISION_REQUESTED |

| REVISION_REQUESTED | 리뷰어 → 개발자 | 수정 요청 (round +1) | IN_PROGRESS |

| APPROVED | 리뷰어 → 팀 리더 | 동료 리뷰 통과 | PENDING_FINAL_QA |

| PENDING_FINAL_QA | 팀 리더 → QA | 최종 품질 검증 요청 | FINAL_QA_PASSED, FINAL_QA_FAILED |

| FINAL_QA_PASSED | QA → 팀 리더 | 모든 검증 통과 | WORKFLOW_COMPLETE |

| FINAL_QA_FAILED | QA → 팀 리더 | 검증 실패, 재지시 필요 | QUEUED (재할당) |

| ESCALATED | 자동 | max_rounds 초과 시 아키텍트 개입 | QUEUED (재설계 후) |

| OVERRIDE | 팀 리더 → 임의 | 강제 개입 (수동 제어) | 모든 상태 |

| WORKFLOW_COMPLETE | 팀 리더 → WF 매니저 | 작업 완료 | (종료) |

                          │            OVERRIDE (강제 개입)           │
                          │         Mayor가 언제든 발동 가능          │

                                           │
                                           ▼ (모든 상태로 전이 가능)

  QUEUED ──→ IN_PROGRESS ──→ PENDING_REVIEW ──→ APPROVED ──→ PENDING_FINAL_QA

    │                              ▼                              ▼
    │                    REVISION_REQUESTED              FINAL_QA_PASSED ──→ WORKFLOW_COMPLETE

                         (재할당 / 재설계)

1.4.6 핵심 루프 2개

내부 루프 (Peer Review Loop):

개발 에이전트와 리뷰 에이전트 간의 코드 리뷰 사이클이다. PENDING_REVIEW ↔ REVISION_REQUESTED 상태를 반복하며, max_rounds를 초과하면 자동으로 ESCALATED로 전이되어 아키텍트(Mayor)가 개입한다.

개발 에이전트 ──(PENDING_REVIEW)──→ 리뷰 에이전트
     ▲                                    │
     │                                    ▼
     └──(REVISION_REQUESTED, round+1)─────┘
              (max_rounds 초과 시 → ESCALATED)

외부 루프 (Final QA Gate):

Peer Review를 통과(APPROVED)한 코드가 E2E 테스터 + 감사관의 최종 검증을 거친다. 실패 시 팀 리더가 원인을 분석하여 재지시(QUEUED)한다.

APPROVED ──→ PENDING_FINAL_QA ──→ FINAL_QA_PASSED ──→ WORKFLOW_COMPLETE
                    │
                    └──→ FINAL_QA_FAILED ──→ QUEUED (재할당)

1.4.7 next_actor 필드와 상태 머신 라우팅

response.jsonl의 next_actor 필드가 상태 머신의 라우팅 키이다. 팀 리더(Mayor)는 이 필드를 읽어 다음에 어떤 에이전트가 행동해야 하는지 결정한다.

| status | next_actor 예시 | Mayor의 행동 |

| --- | --- | --- |

| QUEUED | agent-implement-1 | 해당 에이전트에 query.jsonl 작성 |

| IN_PROGRESS | self | 대기 (폴링) |

| PENDING_REVIEW | agent-reviewer | 리뷰어에게 query.jsonl 작성 |

| REVISION_REQUESTED | agent-implement-1 | 개발자에게 수정 query.jsonl 작성 |

| APPROVED | mayor | Mayor가 Final QA 단계로 전환 |

| PENDING_FINAL_QA | agent-qa-e2e | QA 에이전트에게 query.jsonl 작성 |

| FINAL_QA_PASSED | mayor | Mayor가 머지 + WORKFLOW_COMPLETE |

| FINAL_QA_FAILED | mayor | Mayor가 원인 분석 후 재할당 |

| ESCALATED | mayor | Mayor가 아키텍트로서 재설계 |

| OVERRIDE | (지정) | Mayor가 강제 지정한 에이전트 |

| WORKFLOW_COMPLETE | workflow-manager | 상위 워크플로우 매니저에 보고 |

1.4.8 history.jsonl 레코드 예시

history.jsonl은 모든 query.jsonl과 response.jsonl 레코드를 시간순으로 누적 기록한다. 에이전트 크래시 후 컨텍스트 복구 시 이 파일을 읽어 전체 이력을 재구성한다.

2. 도구별 상세 분석

2.1 Beads (bd) — 에이전트 메모리 & 태스크 관리

"AI 코딩 에이전트가 실제로 사용하고 싶어하는 TODO 시스템" — Steve Yegge

개요: Beads는 Git-backed 이슈 트래커로, AI 코딩 에이전트에게 영속적 메모리를 제공한다. 세션이 종료되거나 에이전트가 크래시해도 .beads/ 디렉토리에 모든 작업 상태가 JSONL + SQLite 하이브리드로 저장되어 있어 즉시 복구할 수 있다.

핵심 메커니즘:

  • JSONL + SQLite 하이브리드 저장소: 빠른 읽기(SQLite)와 Git 친화적 변경 추적(JSONL)을 동시에 달성
  • 적응형 ID 시스템: 짧은 접두사 기반 ID (예: gt-abc12)로 에이전트가 쉽게 참조
  • bd prime: 세션 시작 시 ~1-2k 토큰의 컨텍스트를 자동 주입하여 에이전트가 현재 상태를 즉시 파악
  • Git-backed: 모든 변경이 Git으로 추적되어 히스토리 완전 보존

    • CLI 명령어 전체 목록:

| 명령어 | 기능 | 사용 예시 |

| --- | --- | --- |

| bd init | 프로젝트에 Beads 초기화 | bd init --quiet |

| bd create | 새 이슈/태스크 생성 | bd create "댓글 API 구현" |

| bd ready | 작업 가능한 태스크 목록 | bd ready |

| bd prime | 세션 컨텍스트 주입 | bd prime (자동 훅으로 실행) |

| bd show | 이슈 상세 보기 | bd show gt-abc12 |

| bd update | 이슈 상태 업데이트 | bd update gt-abc12 --status done |

| bd stats | 통계 확인 | bd stats --actor=gastown/polecats/* |

| bd doctor | 진단 및 자동 수정 | bd doctor --fix |

| bd admin compact | 데이터 압축 | bd admin compact |

| bd setup <editor> | 에디터 통합 설정 | bd setup claude |

2.2 Gas Town (gt) — 멀티 에이전트 오케스트레이터

"AI 에이전트 작업을 구조화된 데이터로 다루는 오케스트레이션 레이어" — Steve Yegge

개요: Gas Town은 20~30개 이상의 AI 에이전트를 동시에 조율하는 워크스페이스 매니저이다. Mayor(시장)가 전체를 지휘하고, Polecat(임시 워커)이 격리된 워크트리에서 실제 작업을 수행하며, Convoy(호송대)가 배치 작업을 추적한다.

역할 체계 (Role Taxonomy):

| 역할 | 설명 | 생명주기 |

| --- | --- | --- |

| Mayor | 전역 조율자, mayor/ 에 위치 | 싱글톤, 영속 |

| Deacon | 백그라운드 감독 데몬 (워치독 체인) | 싱글톤, 영속 |

| Witness | Rig별 Polecat 생명주기 관리자 | Rig당 1개, 영속 |

| Refinery | Rig별 머지 큐 처리기 | Rig당 1개, 영속 |

| Polecat | 임시 워커 (자체 워크트리 보유) | 일시적, Witness 관리 |

| Crew | 영속 워커 (자체 클론 보유) | 장기, 사용자 관리 |

| Dog | Deacon 헬퍼 (인프라 태스크) | 일시적, Deacon 관리 |

Gas Town은 gt sling 명령의 --model 플래그를 통해 태스크별로 다른 모델을 배정할 수 있다. 단, 이는 같은 엔진(Claude Code) 내에서의 모델 변경(sonnet vs opus)이며, 엔진 자체 변경(Claude → Gemini → OpenCode)은 Ralphy가 담당한다.

Propulsion Principle (추진 원칙):

2.3 Ralphy — 멀티엔진 병렬 실행기

"Autonomous AI coding loop. Runs AI agents on tasks until done."

개요: Ralphy는 8개 AI 코딩 엔진을 자유롭게 선택하여 태스크를 병렬 실행하는 CLI 도구이다. 각 에이전트는 격리된 Git 워크트리에서 독립적으로 작업하며, PRD(Product Requirements Document) 기반으로 태스크 목록을 순회하며 완료될 때까지 루프를 돈다.

지원 엔진 (8개):

| 엔진 | CLI 명령 | 권한 플래그 | 출력 |

| --- | --- | --- | --- |

| Claude Code | claude | --dangerously-skip-permissions | tokens + cost |

| OpenCode | opencode | full-auto | tokens + cost |

| Codex | codex | N/A | tokens |

| Cursor | agent | --force | duration |

| Qwen | qwen | --approval-mode yolo | tokens |

| Factory Droid | droid exec | --auto medium | duration |

| GitHub Copilot | copilot | --yolo | tokens |

| Gemini CLI | gemini | --yolo | tokens + cost |

핵심 CLI 플래그:

| 플래그 | 기능 |

| --- | --- |

| --prd PATH | 태스크 파일/폴더 (기본: PRD.md) |

| --yaml FILE | YAML 태스크 파일 |

| --json FILE | JSON 태스크 파일 |

| --github REPO | GitHub 이슈를 태스크 소스로 |

| --model NAME | 모델 오버라이드 |

| --parallel | 병렬 실행 모드 |

| --max-parallel N | 최대 에이전트 수 (기본: 3) |

| --sandbox | 경량 샌드박스 모드 (심볼릭 링크) |

| --branch-per-task | 태스크별 브랜치 생성 |

| --create-pr | PR 자동 생성 |

| --draft-pr | 드래프트 PR 생성 |

| --no-merge | 자동 머지 건너뛰기 |

| --base-branch NAME | 베이스 브랜치 지정 |

| --browser | agent-browser 활성화 |

| --no-tests / --no-lint / --fast | 테스트/린트 건너뛰기 |

| --max-retries N | 태스크당 재시도 횟수 (기본: 3) |

2.5 Langfuse — LLM 옵저버빌리티 & 트레이싱

개요: Langfuse는 LLM 애플리케이션의 트레이싱, 비용 추적, 품질 평가를 제공하는 오픈소스 옵저버빌리티 플랫폼이다. 멀티 에이전트 환경에서 각 에이전트의 토큰 사용량, 응답 시간, 비용, 품질을 실시간으로 모니터링한다.

핵심 기능:

| 기능 | 설명 |

| --- | --- |

| 트레이싱 | 에이전트별 LLM 호출 추적 (입력/출력/토큰/비용) |

| 비용 추적 | 모델별, 에이전트별, 태스크별 비용 집계 |

| 품질 평가 | 사용자 피드백, 자동 평가 스코어 |

| 대시보드 | 실시간 모니터링 대시보드 |

| 세션 관리 | 에이전트 세션별 그룹화 |

| 프롬프트 관리 | 프롬프트 버전 관리 및 A/B 테스트 |

설치 및 설정:

# Python SDK
pip install langfuse

# 또는 Self-hosted (Docker)
docker compose up -d  # langfuse docker-compose.yml

환경 변수:

export LANGFUSE_SECRET_KEY="sk-..."
export LANGFUSE_HOST="https://cloud.langfuse.com"  # 또는 self-hosted URL

트레이싱 코드 예시 (래퍼 스크립트 ):

from langfuse import Langfuse

langfuse = Langfuse()

def trace_agent_task(agent_name, engine, model, task_title, bead_id):
    """에이전트 태스크 실행을 Langfuse로 트레이싱"""
    trace = langfuse.trace(
        name=f"agent-task-{bead_id}",
        metadata={
            "agent": agent_name,
            "engine": engine,
            "model": model,
            "task": task_title,
            "bead_id": bead_id
        },
        tags=["ralphy", engine, model]
    )
    return trace

def log_completion(trace, tokens_in, tokens_out, cost, status):
    """태스크 완료 시 결과 기록"""
    trace.update(
        output={"status": status},
        metadata={
            "tokens_in": tokens_in,
            "tokens_out": tokens_out,
            "cost_usd": cost
        }
    )
    langfuse.flush()

#!/usr/bin/env python3
"""Ralphy 에이전트 실행을 Langfuse로 트레이싱하는 래퍼"""

import os, sys, json, subprocess, time
from langfuse import Langfuse

langfuse = Langfuse()

def main():
    agent_name = sys.argv[1]   # e.g., "agent-1"
    engine = sys.argv[2]       # e.g., "claude"
    model = sys.argv[3]        # e.g., "sonnet"
    task = sys.argv[4]         # e.g., "댓글 API 구현"
    bead_id = sys.argv[5]      # e.g., "gt-abc12"

    trace = langfuse.trace(
        name=f"ralphy/{agent_name}",
        session_id=f"convoy-{os.environ.get('CONVOY_ID', 'unknown')}",
        metadata={
            "agent": agent_name,
            "engine": engine,
            "model": model,
            "task": task,
            "bead_id": bead_id
        },
        tags=["ralphy", engine, model]
    )

    start = time.time()
    # 실제 에이전트 실행은 Ralphy가 담당
    # 이 스크립트는 시작/종료 트레이싱만 기록
    trace.update(
        output={"status": "started", "duration": time.time() - start}
    )
    langfuse.flush()

if __name__ == "__main__":
    main()

9. 트러블슈팅 및 FAQ

Q1: Gas Town과 Ralphy의 역할이 겹치지 않나요?

A: 겹치는 부분이 있지만 역할이 다르다.

| 기능 | Gas Town | Ralphy |

| --- | --- | --- |

| 오케스트레이션 (계획/조율) | 주 담당 (Mayor) | 없음 |

| 에이전트 생명주기 관리 | 주 담당 (Witness) | 기본적 |

| 멀티 엔진 지원 | Claude Code 내 모델 변경만 | 8개 엔진 자유 선택 |

| 병렬 실행 | Convoy + Polecat | --parallel |

| 영속 상태 | Git-backed (Beads) | 없음 (세션 기반) |

| 스케일 | 20~30+ 에이전트 | 3~5개 적정 |

결론: Gas Town Mayor가 전체를 지휘하고, 다른 엔진이 필요한 작업만 Ralphy에 위임하는 B안(하이브리드)이 최적이다.

Q2: Beads 없이 Gas Town만 쓸 수 있나요?

A: 아니다. Gas Town은 Beads를 태스크 관리 레이어로 필수 의존한다. gt sling으로 할당하는 작업이 Beads 이슈이고, Convoy가 추적하는 것도 Beads 이슈이다.

Q3: Ralphy의 --sandbox 모드와 Gas Town의 워크트리 차이는?

A: Ralphy의 --sandbox는 심볼릭 링크로 node_modules 등을 공유하여 빠르게 격리 환경을 만든다. Gas Town의 워크트리는 Git 네이티브 워크트리로 완전한 Git 히스토리를 보존한다. 대규모 모노레포에서는 Ralphy의 --sandbox가 빠르고, Git 작업이 필요하면 Gas Town 워크트리가 적합하다.

Q4: Langfuse 대신 다른 모니터링 도구를 쓸 수 있나요?

A: 가능하다. 대안으로 LangSmith(LangChain), Helicone, Braintrust 등이 있다. 다만 Langfuse는 오픈소스이고 self-hosted가 가능하여 비용과 데이터 주권 면에서 유리하다.

Q5: CodeRabbit 무료 플랜으로 충분한가요?

A: 오픈소스 프로젝트는 무료이다. 프라이빗 리포는 유료 플랜이 필요하며, Pro 플랜($12/월/사용자)부터 무제한 리뷰를 지원한다. gtr CLI는 완전 무료 오픈소스이다.
